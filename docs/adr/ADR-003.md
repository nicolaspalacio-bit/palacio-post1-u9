# ADR-003: Empleo de Clock Fijo como Fake Determinista frente a Mocking de Tiempo

## Estado
Aceptado

## Contexto
El metodo `enviarRecordatoriosPendientes()` calcula una ventana de tiempo estricta:
- Limite inferior: instante actual (`ahora = LocalDateTime.now(clock)`)
- Limite superior: exactamente 24 horas hacia el futuro (`en24Horas = ahora.plusHours(24)`)

Si el servicio hiciera uso directo de llamadas estaticas del sistema como `LocalDateTime.now()` (equivalente a `Clock.systemDefaultZone()`), cualquier asercion sobre los argumentos pasados al repositorio (`CitaRepository.findByFechaHoraCitaBetween...`) seria inherentemente no determinista: el resultado cambiaria segundo a segundo, hora a hora y variaria segun la zona horaria del servidor o runner donde se ejecute la suite de pruebas.

## Decision
Se adopta el patron de inyeccion de tiempo basado en la abstraccion `java.time.Clock`:

1. **En codigo de produccion:** Se provee un bean en `ClockConfig`:
   ```java
   @Bean
   public Clock clock() {
       return Clock.systemDefaultZone();
   }
   ```
2. **En pruebas unitarias e integracion:** Se inyecta un Fake determinista mediante `Clock.fixed(...)`:
   ```java
   Clock clockFijo = Clock.fixed(Instant.parse("2026-08-10T09:00:00Z"), ZoneId.of("UTC"));
   ```
   En pruebas de integracion `@SpringBootTest`, se sobrescribe el bean en una clase estatica interna anotada con `@TestConfiguration` y `@Primary`.

## Alternativas Descartadas

1. **Uso de llamadas estaticas directas (`LocalDateTime.now()`):**
   - Descartado porque introduce efectos secundarios temporales no controlados en la suite de pruebas, violando el principio F.I.R.S.T. (Repeatable).

2. **Mockear `Clock` con Mockito (`mock(Clock.class)`):**
   - Descartado porque `java.time.Clock` es una clase abstracta compleja. Mockearla requeriria configurar individualmente llamadas a `instant()` y `getZone()`, generando codigo ruidoso, acoplado y propenso a excepciones si metodos internos del JDK invocan operaciones no mockeadas. `Clock.fixed` es una implementacion real ya suministrada por el JDK, por lo que mockearla seria un claro anti-patron.

3. **Uso de librerias de bytecode manipulation como Joda-Time o PowerMock:**
   - Descartado por ser innecesario, fragil ante actualizaciones de JVM y considerado una mala practica arquitectonica cuando el JDK moderno ya provee `java.time.Clock`.

## Consecuencias
- **Positivas:**
  - Pruebas 100% deterministas y reproducibles en cualquier zona horaria o momento del anio.
  - Permite verificar con precision milimetrica limites exactos de fechas mediante `ArgumentCaptor` (`2026-08-10T09:00` a `2026-08-11T09:00`).
  - Diseno limpio donde la fuente del tiempo se trata como una dependencia explicita.
- **Negativas:**
  - En Spring Boot 3, sobreescribir el bean `Clock` en pruebas de integracion requiere habilitar `spring.main.allow-bean-definition-overriding=true` en la configuracion de prueba.
