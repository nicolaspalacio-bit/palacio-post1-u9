# ADR-002: Inversion de Dependencias (DIP) y Composition Root para Canales de Notificacion

## Estado
Aceptado

## Contexto
En la Parte 2 del laboratorio se introdujo la funcionalidad `enviarRecordatorioUrgente(Long citaId)`. En su version inicial, el metodo instanciaba directamente sus dependencias dentro de su cuerpo:
```java
ReminderChannel canalUrgente = new SmsReminderChannel(new TwilioNotificadorSmsGateway());
```
Esta construccion directa viola de manera explicita el Principio de Inversion de Dependencias (DIP, Dependency Inversion Principle) de SOLID por las siguientes razones:
1. El modulo de alto nivel (`CitaReminderServiceImpl`) pasa a depender directamente de clases concretas de bajo nivel (`SmsReminderChannel` y `TwilioNotificadorSmsGateway`) en lugar de depender de abstracciones (`ReminderChannel`).
2. Imposibilita la prueba unitaria aislada: ante un fallo simulado del gateway o una excepcion de red, resulta imposible interceptar o sustituir la llamada sin recurrir a manipulacion compleja de bytecode (`Mockito.mockConstruction`), lo cual es considerado un sintoma de mal diseno.
3. Se viola el Principio Abierto/Cerrado (OCP), pues alterar el canal urgente exigiria modificar la clase del servicio.

## Decision
Se refactoriza la implementacion moviendo la construccion de dependencias concretas al Composition Root de la aplicacion (`CanalUrgenteConfig`) e inyectando la abstraccion `ReminderChannel` calificada en el constructor de `CitaReminderServiceImpl`:

1. Se crea la clase de configuracion `CanalUrgenteConfig` anotada con `@Configuration`:
   ```java
   @Bean
   public ReminderChannel canalUrgente(NotificadorSmsGateway gateway) {
       return new SmsReminderChannel(gateway);
   }
   ```
2. Se actualiza el constructor de `CitaReminderServiceImpl` para recibir `@Qualifier("canalUrgente") ReminderChannel canalUrgente`.
3. El metodo `enviarRecordatorioUrgente` utiliza el colaborador inyectado, eliminando cualquier sentencia `new`.

## Alternativas Descartadas

1. **Uso de `Mockito.mockConstruction(...)` en pruebas unitarias:**
   - Descartado porque encubre la mala practica arquitectonica adaptando la herramienta de prueba a un codigo mal disenado, en lugar de corregir la arquitectura subyacente. La comunidad profesional desaconseja el uso de herramientas invasivas cuando una simple inyeccion por constructor resuelve la testabilidad.

2. **Inyeccion por campo mediante `@Autowired`:**
   - Descartado porque dificulta la instanciacion manual en pruebas unitarias puras fuera del contenedor de Spring y oculta las verdaderas dependencias de la clase. La inyeccion por constructor es la practica estandar recomendada en Spring Boot 3+.

## Consecuencias
- **Positivas:**
  - Habilitacion inmediata de pruebas unitarias para escenarios de contingencia, tales como `enviarRecordatorioUrgente_gatewayFalla_noMarcaComoEnviado()`.
  - El servicio permanece desacoplado de la implementacion concreta de SMS y del proveedor externo Twilio.
  - El único punto del sistema donde existe un `new` para el canal urgente reside en el Composition Root (`CanalUrgenteConfig`), permitiendo intercambiar proveedores en produccion sin alterar una sola linea de logica de negocio.
- **Negativas:**
  - Al coexistir multiples beans de tipo `ReminderChannel` en el contexto de Spring, se requiere el uso explicito del calificador `@Qualifier("canalUrgente")` para evitar ambiguedades de autowiring.
